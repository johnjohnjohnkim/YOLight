# Milestones: YOLight

Goal: automatic room lighting from a camera that is reliable in a real room (lights turn off when you leave), easy for anyone to set up, and shown off through a zero-install demo page for people who will not run it themselves.
Out of scope: training a custom doorway model, depth sensing (RealSense), mic fusion, multi-room, headless service mode (all parked under Unscheduled below).
Milestones are grouped by README version (V1 to V5). The order of work is NOT the version order: the lights-not-turning-off bug lives in V3, so V3 comes first, then the retrospective V1/V2 tests, then V4.

## Loop rules
Branch: `dev` (branched from `goveeServer`). Commit and push only to `dev`, never to `main` or `goveeServer`.
- Work one milestone at a time, in order.
- A milestone is done only when its done-check passes. Run it and show the output.
- When a milestone is done, in this order:
  1. Fill in its Report below and tick its box.
  2. REVIEW: spawn a reviewer agent told to be a harsh, specific code reviewer (correctness, tests that cannot fail, simplicity, naming, error handling, and whether the done-check really proves the milestone). Fix what it finds and rerun the checks; at most 3 rounds, then record what remains in the Report.
  3. Run the `/journal` skill with the milestone name as its scope; entries go in `journal/`. Link the entry from the Report. If the Skill tool refuses, write the full Report and add `Journal: pending`.
  4. Update the progress log in `HANDOFF.md` (git-ignored).
  5. Commit with a message naming the milestone and run `git push origin dev`. Never push if tests fail. Never force-push.
  6. Send a push notification, then continue.
- STOP LINE: stop after milestone V2.1 is committed and journaled, notify, and wait for "go" before V4.
- If blocked, or the done-check cannot pass after a reasonable effort, STOP and notify with what you tried. Do not weaken the check.
- No AI attribution in commits or PRs (no `Co-Authored-By`, no "Generated with" line).
- Never commit `.env`, API keys, `door_zone.json`, model weights or camera footage of people other than the user. Never print `.env`.
- Never force anything, delete outside the project, or spend money without asking.
- Do not edit this file's goals or checks. Only tick boxes and fill in reports.

## V3: Cloud control + activation gate (current version, where the real work is)

### V3.1 Fix: lights do not turn off when I leave  [ ]
Why: reproduced offline against the real `OccupancyTracker`: a fast exit that skips the doorway section, leaving the frame away from the door, and being occluded for more than 15 frames then leaving all leave `room_count=1`, so lights stay on forever. Causes: exits only count mid-doorway; reappearing after a loss counts as a new entry so the count only drifts up; nothing resets the count; no confidence filter so ghost detections count as people.
Work: move the occupancy logic into a pure `occupancy.py` (no cv2/torch imports, injectable clock); make presence time-based (seconds, not frames) with an "empty for N seconds -> off" fallback; count an exit from last-seen position and direction, not only a mid-doorway vanish; stop treating a reappearance as a new entry when the person was never counted out; add a person-confidence filter; add `requirements-dev.txt` (pytest); remove `tests/`, `*.json` and `*[tT]est*` from `.gitignore` (keep `door_zone.json` ignored) so tests are tracked.
Touches: `occupancy.py` (new), `tracker.py`, `tests/test_occupancy.py` (new), `requirements-dev.txt`, `.gitignore`
Blockers: none
Done-check: `venv\Scripts\python -m pytest tests/test_occupancy.py -q` -> all pass, including replay tests for: proper exit through the doorway, fast exit skipping the doorway, leaving far from the door, occluded >15 frames then exiting, enter/exit/re-enter, and a ghost detection that must not count. Each replay must end with lights off after the timeout. Then run `python tracker.py` in the real room, walk out, and note in the Report how many seconds until the lights went off.
Report:

### V3.2 Reliable light control  [ ]
Why: from the code review: the `requests` calls have no timeout (a thread can hang forever); `ThreadPoolExecutor(max_workers=0)` raises when there are no devices; LAN discovery is commented out in `tracker.py` so the fallback never works; on/off threads can finish out of order; `lights_on` is flipped before the command succeeds, so a failed call leaves it wrong forever; non-light cloud devices cause errors; `activation_on` calls an undefined `_activation`.
Touches: `server.py`, `control.py`, `tracker.py`, `tests/test_server.py`
Blockers: none for tests (HTTP and sockets are mocked); the final live check needs the user's lights and `.env`.
Done-check: `venv\Scripts\python -m pytest tests/test_server.py -q` -> pass, with tests for: timeout set on every request, zero devices does not raise, cloud failure falls back to LAN, the latest command wins when two are sent quickly, a failed command leaves the desired state to be retried, non-light devices are skipped. Then `venv\Scripts\python serverTest.py` turns the user's lights off (run by the user or confirmed by them).
Report:
